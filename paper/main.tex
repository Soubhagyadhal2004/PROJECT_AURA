\begin{abstract}
Assistants that keep long-term memory about their user increasingly ask for approval before they change what they believe. We study what such an approval gate protects and what it cannot, in a local assistant (\aura) whose language-model extractor proposes add, update, retire and forget operations over a retrieval-selected list of candidate memories. We make three contributions. First, we separate wrong writes from missed updates and locate the second failure before the gate: an operation on a memory that the extractor was not shown is discarded, so an update succeeds only if its target reaches the prompt. In simulation the gate removes \destroyRedMin--\destroyRedMax\% of the true facts that automatic application destroys, at \gatePromptsMin--\gatePromptsMax\ review prompts per 100 turns, but leaves stale facts unchanged. Second, we define final-prompt reachability on change events and measure which parts of candidate selection determine it, on a new test set of \selPersonas\ personas (\selEventsTotal\ change events per store size) with ablations, same-size and keyword baselines, and change messages that contain none of the selection's cue words. With 350 unrelated memories the default selection reaches \selDefault\ of targets; an adaptive selection (per-sentence search, no minimum score, more candidates on a change cue) reaches \selAdaptive, but a plain list of the 24 best matches without a minimum score reaches \selNominKk\ (difference \selCAdaVsNk, Holm $p=\selCAdaVsNkP$). The adaptive selection shows \selCandSaving\% fewer candidates, is weaker on messages without cue words, and \selMissedAllPct\% of targets are reached by none of \selNConditions\ selection variants; keyword (BM25) and fused rankings do no better than the plain list, while reranking its 50 best matches with a cross-encoder reaches \selRerank\ at the same list size (\selRNk), leaving \selMissedAllRerankPct\% of targets out of reach of every method tested. Third, with two real Gemini extractors (12 personas each) the target was missing from the prompt in \candMissABase\ and \candMissBBase\ of 136 change turns with the default selection and in none with the adaptive selection (run together with the re-proposal rule, which does not affect selection); under the gate, stale facts per persona fell from about 1 to 0 (sign test $p=\realAgatestaleP$ and $\realBgatestaleP$) at about \tokInc\% more prompt tokens. A rule that re-proposes rejected changes gave no measurable benefit, and a 30-question LongMemEval check moved in the same direction without significance ($p=\lmegateP$). Code, test sets and raw results are released.
\end{abstract}

\section{Introduction}
Large language model (LLM) assistants that remember facts about their user across conversations must decide, after every message, whether to add a fact, change one they already hold, or drop one. Mistakes are costly in two different ways. A \emph{wrong write} replaces or removes something that was true (``moved to Pune'' overwrites the true employer), and a \emph{missed update} leaves an outdated value active after the user has said that it changed. A growing line of work treats wrong writes as a governance problem and proposes checks before a memory is stored \cite{lam2026ssgm}. A direct form of such a check is to ask the user: changes to existing memories become proposals that the user accepts or rejects, and old values are kept as history.

This paper starts from a simple observation about where such a gate sits. It acts on the operations that the extractor model \emph{returns}. An update that the extractor never produces cannot be proposed, and therefore cannot be approved. In a retrieval-based design the extractor can change only the memories that are placed in its prompt, so the choice of these candidates bounds how many updates are possible at all. We therefore ask three questions about a user-controlled memory: (Q1) How much of the damage of extractor errors does the gate remove, and at what cost in user prompts? (Q2) How often is the memory that a change refers to visible to the extractor, and how does this depend on the size of the store and on how the candidates are chosen? (Q3) Does a better candidate selection translate into fewer stale facts with real models, and what does it cost?

We study these questions in \aura, a local assistant with a SQLite memory store, local sentence embeddings and a Gemini extractor, using the assistant's real server code throughout. The paper makes three contributions:
\begin{enumerate}
\item \textbf{Failure isolation.} We separate wrong writes from missed updates and show where each is decided. Because \aura\ discards any operation that names a memory the extractor was not shown, the success of a change factors exactly into whether its target reaches the prompt and whether the change is then proposed and accepted (Sec.~\ref{sec:problem}); the gate acts only on the second factor. Under a controlled error model the gate cuts destroyed true facts by \destroyRedMin--\destroyRedMax\% but leaves stale facts essentially unchanged (Sec.~\ref{sec:policies}).
\item \textbf{Measurement of target reachability and of what drives it.} We define reachability on the final extractor prompt for known change events, distinguish it from retrieval recall, and measure it over store sizes, message forms and kinds of change on two test sets (Sec.~\ref{sec:reach}). A controlled study on a new test set of \selPersonas\ personas with \selNConditions\ selection variants, including same-size, keyword (BM25) and fused baselines and change messages held out from the selection's cue words, shows that removing the minimum score and searching per sentence each add about 0.1, that more candidates on a change cue add almost nothing on their own, that the adaptive selection reaches the same share as a plain larger list while showing \selCandSaving\% fewer candidates, that keyword and fused rankings do no better than the plain list, that a cross-encoder reranker does better at the same list size, and that about one target in thirteen stays out of reach of every method tested (Sec.~\ref{sec:selection}).
\item \textbf{End-to-end evidence with real models, with costs.} With two Gemini extractors we evaluate the adaptive selection (F2) and a re-proposal rule (F1) in a paired ablation: with F2 (run together with F1) no change target was missing and the stale facts under the gate disappeared, at about \tokInc\% more prompt tokens; F1 alone showed no measurable benefit (Sec.~\ref{sec:ablation}--\ref{sec:real}). An external LongMemEval check is reported with its limits (Sec.~\ref{sec:lme}). The harness, both test-set generators and all raw results are released.
\end{enumerate}
We do not claim to be the first to study memory-update failures, omissions or retrieval before updating; recent work addresses these from other angles (Sec.~\ref{sec:related}). Our contribution is narrower: a measured account of target visibility as a bottleneck in an approval-gated, retrieval-based update pipeline.

A concrete case from our data (Sec.~\ref{sec:example}) shows the problem. A persona says ``I drive a Seltos'' in one session and, three sessions later, ``I sold my old car and bought a Swift.'' With default settings the extractor was shown neither the stored ``Seltos'' memory (the sentence is a poor match for it) nor a reason to look for it; it added ``bought a Swift'' as a new fact, and the outdated Seltos memory stayed active. The review gate never saw an update to approve. The same persona under the new selection produced the update, the user approved it, and the history was kept.

The rest of the paper is organised as follows. Section~\ref{sec:related} places the work among related studies, Section~\ref{sec:problem} defines the problem and the quantities we measure, Section~\ref{sec:system} describes the memory system, and Section~\ref{sec:method} the evaluation. Sections~\ref{sec:policies}--\ref{sec:lme} give results in the order policies, retrieval, reachability, selection components, ablation, real extractors and LongMemEval; Sections~\ref{sec:discussion}--\ref{sec:future} discuss implications, limits and future work.

We deliberately keep claims narrow. The personas are synthetic and English, the real-model samples are small, the user is simulated, and no user study was run (Sec.~\ref{sec:threats}).

\section{Related Work}
\label{sec:related}
\textbf{Benchmarks.} LoCoMo evaluates very long agent--agent conversations with question answering, summarisation and multimodal tasks \cite{maharana2024locomo}. LongMemEval benchmarks chat assistants on five long-term memory abilities, among them reasoning about updated facts, and splits memory design into indexing, retrieval and reading \cite{wu2024longmemeval}. We use LongMemEval's knowledge-update questions as an external check (Sec.~\ref{sec:lme}).

\textbf{Retrieve-then-update pipelines.} Mem0 extracts candidate facts from a conversation, retrieves the most similar stored memories for each, and lets a language model choose to add, update, delete or leave memory unchanged \cite{chhikara2025mem0}. \aura's default pipeline follows the same pattern, with two differences: changes to existing memories wait for the user, and old values are kept. Our results therefore bear on any pipeline of this shape: whatever the retriever does not place before the model cannot be updated.

\textbf{Learning reliable memory updates.} TrustMem trains a memory agent that reads a chunk of input together with the current memory and emits write, revise and prune actions \cite{yang2026trustmem}. A frozen language model, the Memory Transition Verifier, scores each transition for \emph{coverage} (information from the current chunk is kept), \emph{preservation} (valid prior memory is not damaged) and \emph{faithfulness} (new content is supported); it sees the chunk, the actions and the memory entries they touch or retrieve. The scores drive Transition-Ranked GRPO, and on MemoryAgentBench, HaluMem and the Mem-$\alpha$ validation set the method reduces transition-level omission, corruption and hallucination by 40.1\%, 79.1\% and 50.0\% against the strongest baseline for each. TrustMem's omission is information from the new input that is not stored; the failure we isolate is different and earlier: the stored record that must change is absent from the updater's input, so no transition on it can be generated. AgeMem exposes add, update and delete operations on long-term memory and retrieve, summary and filter operations on short-term context as tools of one policy, trained in three stages with a step-wise GRPO, and evaluates on ALFWorld, SciWorld, PDDL, BabyAI and HotpotQA \cite{yu2026agemem}; which records the policy sees when it updates is part of what it learns, and is not measured separately. Supersede maintains a bounded notes memory that the agent rewrites after each session; on the 78 knowledge-update questions of LongMemEval, bounded memory lowers accuracy from 92\% to 77\% for a frontier model (paired McNemar $p<0.005$) and from 82\% to 63\% for a smaller one, the gap grows with conversation length rather than shrinking with more memory, and GRPO fine-tuning of a 3B model raises held-out supersession accuracy from 9.0\% to 16.7\% in a single run \cite{patel2026supersede}. Because the whole notes field is rewritten, no retrieval step stands between memory and updater there; the gap Supersede measures is one of maintenance, while ours is one of visibility. Both papers support the premise that stale facts are a real, distinct failure, and Supersede's finding that bounded memory stays below full context matches our LongMemEval observation. PAMU tracks evolving preferences as a vector, combining sliding-window averages and exponential moving averages with a change-detection signal, and evaluates on LoCoMo \cite{sun2026pamu}; it updates a preference representation, not discrete stored facts.

\textbf{Retrieval that shapes memory and access to it.} REALM organises memory as a heterogeneous graph, retrieves evidence with adaptively composed graph-search operations and reconsolidates memory from retrieval feedback, reaching 75.97\% on LoCoMo and 65.11\% on LongMemEval \cite{song2026realm}. Retrieval there serves answering and drives reorganisation; it is not used to choose the record that a requested change must target. MemGate places a 9M-parameter, query-conditioned gate between a vector store and the model that decides which retrieved memories are admitted \cite{zhang2026memgate}; on a personal-agent environment with GPT-4o-mini it lowers cross-domain leakage from 27.0\% to 3.5\% and jailbreak success from 16.8\% to 4.4\%, while LoCoMo F1 rises from 38.9 to 40.8. MemGate filters what reaches a response; a filter placed after candidate selection can only remove candidates, so it cannot raise the reachability we study, although it could make larger candidate lists safer.

\textbf{Governance and error propagation.} Lam et al.\ propose a governance framework that separates memory updates from task execution and applies consistency checks and permission controls before storage \cite{lam2026ssgm}. Xiong et al.\ show that adding and deleting stored experiences changes agent behaviour and that errors can compound through retrieval \cite{xiong2025memory}; Xiao et al.\ trace how errors entering through memory updates persist over turns \cite{xiao2026errors}; Chu surveys security threats to agents by layer \cite{chu2026survey}.

\textbf{Positioning.} These studies establish that reliable long-term memory needs more than storing and retrieving similar text, and that update failures and stale facts are measurable problems. The present work does not claim to introduce update reliability or retrieval before updating. It examines one narrower condition in user-controlled, retrieval-based updating: the stored record that must change may be absent from the updater's prompt, in which case no approval step can repair the miss. We measure this condition directly, separate it from the gate's effect, and test which parts of an inexpensive, inference-time change to candidate selection address it. TrustMem, AgeMem, Supersede, PAMU, REALM and MemGate were read in full for this paper; the other works were read at the level of their abstracts. A more systematic search for work on update-target retrieval may find closer studies, and we make no priority claim.

\section{Problem Definition}
\label{sec:problem}
Let $U$ be the set of change events in a conversation: user messages that require an existing memory to be updated, retired or forgotten. For an event $u$, let $m^*_u$ be the stored record that must change and $C_u$ the set of memories in the extractor's final prompt. In \aura, $C_u = S_k(x_u) \cup R_8$, where $S_k(x_u)$ are the at most $k$ best search matches for the message $x_u$ that pass the minimum score and $R_8$ are the eight most recently confirmed memories. We define \emph{final-prompt reachability} as
\begin{equation}
\mathrm{CR} = \frac{1}{|U|}\sum_{u\in U} \mathbf{1}\left[m^*_u \in C_u\right].
\end{equation}
Events without an existing target (new facts, small talk) never enter the denominator.

\textbf{An exact factorisation.} \aura\ applies an update, retire or forget operation only if the memory identifier it names was in $C_u$; any other identifier is discarded. Let $R_u$ be the event $m^*_u\in C_u$, $O_u$ the event that the extractor returns the correct operation on $m^*_u$, $A_u$ the event that the user accepts it, and $S_u$ the event that the change takes effect. Because $S_u$ requires $O_u$, and $O_u$ can only take effect if $R_u$ holds,
\begin{equation}
P(S) = P(R)\,P(O \mid R)\,P(A \mid O, R).
\end{equation}
The gate acts on the last factor (it blocks wrong operations and may lose correct ones through user error); it cannot change $P(R)$. This is the formal version of the paper's title. (The factorisation concerns changes proposed by the extractor; \aura's optional ``is this still true?'' checks, which ask the user directly, are a separate path and were not used in any experiment.) When $R_u$ fails, the extractor often stores the new value as a fresh memory, so the outdated record stays active beside it: a missed update usually appears as a conflict, not as silence.

\textbf{Reachability versus retrieval recall.} If there were no minimum score and no recent-memory slots, CR would equal Recall@$k$ of the target on change events. \aura's selection differs in both respects: the minimum score can remove a target that ranks within the top $k$, and the recent slots can add a target that search did not find. We therefore report, next to CR, the share of targets within the top $k$ of the unfiltered ranking (Sec.~\ref{sec:selection}). CR is not a new kind of retrieval metric; it is recall measured where it matters for updating, on the final prompt and only on events that require a change.

\textbf{Quantities reported.} We keep four quantities apart: reachability (is $m^*_u$ in $C_u$?), retrieval quality (how search ranks the target), update correctness (given $R_u$, is the right change proposed and accepted?), and final memory quality (after many turns, are facts current, supported and preserved?). The simulations and real runs measure the last; Sections~\ref{sec:reach} and~\ref{sec:selection} measure the first two; the real runs also report missing targets per change turn.

\section{System: User-Controlled Memory in \aura}
\label{sec:system}
\subsection{Memory store and operations}
\aura\ keeps memories in SQLite. A memory has text, a category (preference, personal, people, work, plan, other), a status (\texttt{active}, \texttt{superseded} or \texttt{outdated}), a pointer to the memory that replaced it, a source and its conversation, and timestamps. After each user message a Gemini model (default \texttt{gemini-3.5-flash-lite}) receives the message and a list of candidate memories and returns operations: \emph{add}, \emph{update} (replace a value), \emph{retire} (the fact no longer holds), or \emph{forget}. An update keeps the old row as \texttt{superseded} with a link to its successor; retire marks the old row \texttt{outdated}. The extractor can refer only to memory identifiers that appear in its prompt.

Table~\ref{tab:model} lists the fields that matter for the evaluation. Nothing is overwritten in place by an update: the old row stays with status \texttt{superseded} and points to its successor, so every change can be audited and, if needed, reversed by the user.

\subsection{Extraction prompt}
After each batch of new user messages the extractor receives the date, the candidate memories as lines of the form \texttt{[id] (category) text}, optional earlier context and the new messages. The instructions tell it to store only what the \emph{user} said or confirmed (preferences, personal details, people, work, plans, routines), not questions, general knowledge, assistant suggestions or one-off requests, to write one short third-person sentence per fact, and to choose among the four operations. The output is constrained to a JSON schema with the fields action, memory\_id, content and category. An operation that names an identifier that was not in the candidate list is ignored by the application. This is the point at which candidate selection limits what can change.

\subsection{The review gate}
When ``ask before changing memories'' is on (the default), \emph{add} operations are applied directly and every operation that touches an existing memory becomes a stored \emph{proposal} (action, target memory, proposed text, conversation). The user accepts or rejects it; nothing changes until then. We call this policy \textbf{gate}. The comparison policies are \textbf{append} (only additions; a changed fact is stored as a second fact), \textbf{auto} (all operations applied at once), and \textbf{gate\,all} (also new facts wait for approval; emulated in the harness, not an \aura\ setting).

\subsection{Candidate selection}
\label{sec:candidates}
The prompt contains candidate memories chosen from the store. By default these are the 12 best search matches for the user's message plus the 8 most recently created memories. Search combines the cosine similarity of MiniLM sentence embeddings \cite{wang2020minilm} (\texttt{all-MiniLM-L6-v2}, run locally) and a lexical overlap score, $0.85\cdot\cos + 0.15\cdot\mathrm{lex}$, and drops matches below a minimum score of 0.25. We evaluate four modes, selected by an environment variable:
\begin{itemize}
\item \textbf{default}: as above;
\item \textbf{no minimum}: the same, without the 0.25 cut-off;
\item \textbf{sentence}: the message is split into sentences and each is searched on its own, so that an unrelated sentence does not dilute the query;
\item \textbf{adaptive} (F2): sentence search without minimum score, and a larger number of matches (up to 24) when the message contains a change cue (words such as ``moved'', ``stopped'', ``no longer'', ``forget'').
\end{itemize}
Using F2 enlarges the prompt (Sec.~\ref{sec:cost}); the minimum score exists to keep unrelated memories out (Fig.~\ref{fig:threshold}). Because F2 bundles three changes, Section~\ref{sec:selection} separates them and compares F2 with plain larger lists of the same size.

\begin{algorithm}[t]
\caption{Candidate selection (modes \emph{default} and \emph{adaptive})}
\label{alg:cand}
\small
\KwIn{user text $x$, mode, store, minimum score $\tau=0.25$}
\KwOut{candidate memories shown to the extractor}
$f \leftarrow 0$ if mode is no-minimum or adaptive, else $\tau$\;
\eIf{mode is sentence or adaptive}{
  $k \leftarrow 24$ if mode is adaptive and $x$ contains a change cue, else $12$\;
  \ForEach{$q \in \{x\} \cup \mathrm{sentences}(x)$}{
    \ForEach{memory $m$ in $\mathrm{search}(q, k, f)$}{keep the best score per memory\;}}
  $R \leftarrow$ the $k$ memories with the best scores\;
}{$R \leftarrow \mathrm{search}(x, 12, f)$\;}
\Return $R \cup$ the 8 most recent memories\;
\end{algorithm}

\subsection{Re-proposal (F1)}
A rejected proposal normally ends the matter. With F1 a rejected change may be proposed again, at most $N$ times, but only after the user has said something new about it (we use $N=2$). The aim is to recover from a rejection that was a slip without nagging the user. Concretely, when the extractor repeats a rejected change, the application compares the time of the last user message with the time of the last rejection and creates a new proposal only if the user has written since and the number of earlier rejections is at most $N$. An identical proposal that is still pending is never duplicated, and a newer proposal for the same memory replaces an older pending one.

\subsection{Simulated extractor and user}
The simulated extractor returns what a correct model would return for the turn, using only the memories shown in the prompt; a change whose target is not shown becomes an add, as a real model would do. Errors are injected at rate $e$: a correct operation is dropped, a distractor becomes a false memory, or a true memory shown to the model is retired or overwritten with a false value. All policies face the same random draws. The simulated user reviews proposals at the end of a session, accepts correct ones and rejects wrong ones, and errs with probability $u$ (default 0.05).

\subsection{Scoring rules}
Memories written by a model are scored by the \emph{values} they mention (for example ``Pune'', ``Swift'', ``6 am''), using the persona's slots and a list of alternative wordings. A memory mentioning a value that is true at the end is \emph{true}. One that mentions a value the user gave earlier and that is no longer true is \emph{stale}, unless it records that the fact ended (``finished the project and is between projects'', after a retire request), which is \emph{ended} and counted as correct. A memory about a distractor value is \emph{hypothetical} when it is worded as a hypothetical, \emph{third-party} when it concerns another person (allowed), and \emph{false} otherwise. A memory that mentions no known value is \emph{other}. The exact lists are given in Appendix~\ref{app:scoring}.

\subsection{Metrics}
\textbf{F1} compares the persona's active memories with the true facts. \textbf{Stale} counts active memories holding a value the user gave earlier that is no longer true. \textbf{False} counts active memories the user never stated about themselves. \textbf{Destroyed} counts true memories, persona and background, that ended up superseded, outdated or deleted by a wrong change; F1 does not see the background memories, so this is the safety metric. \textbf{Prompts/100} is the number of review cards per 100 user turns. \textbf{Reachability} is the share of change requests whose target memory is among the extractor's candidates. \textbf{Prompt tokens} are summed over a persona run. With $T$ the set of persona facts that are true at the end, $A$ the set of active persona memories scored true or ended, and $P$ the set of all active persona memories, precision is $|A|/|P|$, recall is the share of $T$ covered, and F1 their harmonic mean. \textbf{Exact state} is 1 for a persona whose final memory has every true fact, no stale and no false fact, and 0 otherwise.

\subsection{Real-model runs and scoring}
Real runs use Gemini as the extractor for 12 personas, one seed, with the simulated user as an oracle ($u=0$), for the policies auto and gate and four variants (baseline, F1, F2, F1+F2). They were repeated for baseline and F1+F2 with a second model (\texttt{gemini-3.1-flash-lite}). Because models word memories freely, a memory is scored by value: the automatic scorer maps each active memory to a persona fact and a label (true, stale, ended, hypothetical, third party, other). The author hand-labelled every memory of the baseline and F1+F2 runs (\agrBaseN\ and \agrBothN\ memories). There were \realExtractions\ extraction calls and \realExtractionErrors\ failed. Requests were rate-limited (12 per minute), each persona was played in its own isolated database, and the extractor was the only part of the system that called the model; the reviewing user was the oracle described above and judged a proposal by the same value-based rules as the scorer. This has a consequence that we discuss with an example (Sec.~\ref{sec:example}): the oracle can reject a correct proposal whose wording the rules do not recognise.

\subsection{Statistics}
Differences between variants are paired by persona and seed. We report the mean difference with a 95\% bootstrap interval (4000 resamples, fixed seed) and an exact two-sided sign test on the non-tied pairs. No correction for multiple tests is applied; the tests run are \simTests\ (simulated ablation) and \realTests\ (real runs), so isolated $p$-values near 0.03 should not be read as findings. Reachability is reported with Wilson intervals \cite{wilson1927}, and agreement between hand and automatic labels with Cohen's $\kappa$ \cite{cohen1960}; since there is a single annotator this measures the scorer against the annotator, not human--human agreement.

\section{Results: Which Part of Candidate Selection Matters}
\label{sec:selection}
The adaptive mode changes three things at once: it searches each sentence, it drops the minimum score, and it shows up to 24 instead of 12 matches when the message contains a change cue. It also shows more candidates, so a fair question is whether a plain larger list would do as well. We answer this on a second, independently generated test set.

\textbf{Test set.} \selPersonas\ personas, each with 12 facts (city, employer, dog's name, sister's city, diet, gym time, language being learned, car, project, coffee, hobby, birthday) whose values and new values are drawn per persona. Each persona has 350 unrelated memories, 30\% of them \emph{similar} (the same relation about another person, such as ``The user's friend Rohan lives in Delhi'') and the rest generic; no unrelated memory mentions any of the persona's values. Stores of $N\in\{0,25,50,100,200,350\}$ unrelated memories are built incrementally, with the persona's facts older than every unrelated memory. Each persona has \selEvents\ change events (44 updates, 28 retires, 8 forgets). Every change is written in a \emph{cue} form, which contains a word from \aura's change-cue list, and a \emph{cue-free} form, which contains none (checked automatically); each form appears as a single sentence and as a mixed turn with two unrelated sentences. This gives \selEventsTotal\ events per store size and \selRows\ event--store pairs. The cue-free half is held out from the design of the cue list and tests whether the adaptive mode depends on wording.

\textbf{Conditions.} Table~\ref{tab:selmain} lists \selNConditions\ selection conditions: the four modes in \aura, four ablations that switch the adaptive mode's parts on one at a time or in pairs, three \emph{same-budget} baselines that always show 24 matches, and four retrieval baselines added after the pre-registered design: BM25 keyword ranking ($k_1=1.2$, $b=0.75$, \aura's tokeniser, only memories sharing a term with the message) with 12 and 24 matches, and reciprocal-rank fusion of BM25 with \aura's ranking, for the whole message and per sentence. All conditions are computed from \aura's own search; for the four modes that exist in \aura, a test confirms that the computed candidate lists are identical to those of \aura's selection code. The server code was not changed.

\textbf{Statistics.} The persona is the unit (\selPersonas). Rates come with persona-clustered bootstrap intervals (10{,}000 resamples). Six comparisons were fixed before the run and are Holm-corrected; they use exact sign tests over personas on paired per-persona rates (Table~\ref{tab:selcomp}). The four comparisons for the added retrieval baselines form a second, separately Holm-corrected family. Other comparisons are labelled exploratory.

\textbf{The default selection.} With 350 unrelated memories the default reaches \selDefault\ of targets [\selDefaultLo, \selDefaultHi], \selDefaultSingle\ for single sentences and \selDefaultMixed\ for mixed turns. It already loses a third of targets at $N=25$ (\selDefaultTwentyfive) and then stays flat (Fig.~\ref{fig:selection}a): the minimum score, not the size of the store, is the main limit. At $N=350$, \selLostFloor\ of targets rank within the top 12 but score below 0.25.

\textbf{Which parts matter.} Removing the minimum score alone adds \selCNominVsDef\ and per-sentence search alone adds \selCSentVsDef\ (both 40 of 40 personas, Holm $p\selCNominVsDefP$). Showing 24 matches on a change cue, with the minimum score kept, adds only \selCCueVsDef: the minimum score leaves most of the extra places empty (the default with $k=24$ shows \selDefaultKkCand\ candidates on average and reaches \selDefaultKk). The adaptive mode, which combines all three, gains \selCAdaVsDef\ over the default.

\textbf{A same-budget baseline matches it.} A plain list of the 24 best whole-message matches without a minimum score reaches \selNominKk, against \selAdaptive\ for the adaptive mode (difference \selCAdaVsNk\ [\selCAdaVsNkLo, \selCAdaVsNkHi], \selCAdaVsNkPos\ personas favouring the adaptive mode and \selCAdaVsNkNeg\ the plain list, Holm $p=\selCAdaVsNkP$). The adaptive mode reaches this level while showing \selCandSaving\% fewer candidates (\selAdaptiveCand\ against \selNominKkCand), because it enlarges the list only on a cue. Its possible advantage over the plain list is per-sentence search on mixed turns (exploratory: \selEMixAdaVsNk, $p=\selEMixAdaVsNkP$, not significant); its clear disadvantage is the dependence on cue words: on cue-free messages it falls back to 12 matches and reaches \selEFreeAdaVsNk\ less than the plain list (exploratory, $p=\selEFreeAdaVsNkP$), and within the adaptive mode cue-free messages are reached \selCAdaFreeVsCue\ less often than cue messages (Holm $p\selCAdaFreeVsCueP$). Combining per-sentence search, no minimum score and 24 matches always gives the highest value, \selSentNominKk\ (exploratory: \selESnkVsNk\ over the plain list).

\textbf{Keyword and fused rankings.} BM25 on its own reaches \selBmTwelve\ with up to 12 matches, more than the default (\selBBmVsDef, Holm $p\selBBmVsDefP$), because it has no minimum score; with up to 24 matches it reaches \selBmTwentyfour, since often fewer than 24 memories share a word with the message (\selBmTwentyfourCand\ candidates on average), and it stays well below the same-size embedding list (\selBBmVsNk). Fusing BM25 with \aura's ranking reaches \selRrf, the same as the plain embedding list (\selBRrfVsNk, Holm $p=\selBRrfVsNkP$), and per-sentence fusion \selSentRrf\ (\selBSentRrfVsSnk\ against per-sentence embedding search, Holm $p=\selBSentRrfVsSnkP$). On this test set, adding keyword evidence does not improve on a larger embedding list. A first BM25 run that kept memories with zero score ranked them in insertion order, which placed the persona's own (oldest) facts first and inflated BM25 strongly; we report only the corrected run and mention this because the artefact is easy to reproduce by accident.

\textbf{A cross-encoder reranker.} As a stronger retrieval baseline we reranked the 50 best whole-message matches of \aura's search (no minimum score) with a cross-encoder (\texttt{ms-marco-MiniLM-L-6-v2}, quantised, run locally) and showed the top 24 plus the recent memories, on the same events and stores at $N=350$. The reranker reaches \selRerank\ [\selRerankLo, \selRerankHi] with \selRerankCand\ candidates, the same number as the plain list: \selRNk\ over the plain list (\selRNkPos\ personas better, \selRNkNeg\ worse, Holm $p\selRNkP$), \selRAda\ over the adaptive mode, and \selRSnk\ over per-sentence search with 24 matches (Holm $p=\selRSnkP$, not significant). Its ceiling is the pool: the target is among the 50 candidates in \selRerankPool\ of events. It is weakest on mixed turns (\selRerankMixed), where per-sentence search helps the other selections; reranking per sentence was not tried. The five reranker comparisons form a third Holm family, added after the pre-registered design; the reranker was run on the authors' machine because its download is blocked in the environment used for the other runs (Table~\ref{tab:selmain}, last row; Fig.~\ref{fig:selection} does not include it).

\textbf{What no variant fixes.} At $N=350$, \selMissedAllPct\% of change events are reached by none of the \selNConditions\ conditions (\selMissedAllRerankPct\% also not by the reranker), and only \selRtwentyfour\ of targets are among the 24 best matches for the whole message even without a minimum score. These are messages that name the new value but share little with the stored sentence, for example a car model mentioned without the word ``car'', or a city statement facing many similar place facts about other people: the car fact is reached in \selCarDefault\ of events by the default and \selCarAdaptive\ by the adaptive mode. Similarity-based candidate lists of this size have a ceiling, and closing the rest needs a different mechanism (Sec.~\ref{sec:discussion}).

\textbf{Relation to the first test set.} The direction of every effect agrees with Sec.~\ref{sec:reach}, but the levels differ between the two test sets (for example, mixed turns are reached \mixedDefault\ of the time there and \selDefaultMixed\ here under the default), because the phrasing of changes and of the surrounding sentences differs. Reachability levels are therefore properties of a system \emph{and} a conversation distribution; comparisons between selections on the same events are the robust result.

\section{Discussion}
\label{sec:discussion}
\textbf{Where the guarantee ends.} The gate provides a guarantee about what is \emph{written}: nothing changes without approval. It provides none about what is \emph{proposed}. In our experiments the second quantity depends on a component that looks like plumbing, the choice of candidate memories, and with default settings it is the main reason that stale facts remain. Evaluating a user-controlled memory by its write accuracy or by the number of approvals alone would miss this.

\textbf{Design implications.} (i) Report reachability alongside accuracy for any extractor-based memory, on change events and on the final prompt. (ii) For the extractor's candidate search, the minimum score is the largest single loss; a search tuned to keep unrelated memories out of \emph{answers} is the wrong default for choosing what an update may touch. (iii) Search per sentence when messages are mixed. (iv) Do not rely on cue words: in our second test set they added almost nothing on their own and made the adaptive mode weaker on messages phrased without them; a plain larger list did as well at a somewhat larger prompt, and reranking that list with a cross-encoder did better. (v) Budget for more prompt tokens (about \tokInc\% with F2 in the real runs) and slightly more review cards.

\textbf{What the gate is for.} The gate is a user-control mechanism as much as a safety mechanism. Every change to what the assistant believes about a person passes a visible decision, old values remain as history, and forgetting is an explicit operation that removes the memory. Our results show what this buys (protection against wrong writes) and what it costs (20--33 prompts per 100 turns in simulation, a little more with F2). They also show a limit: the gate's protection is only as good as the user's attention (Table~\ref{tab:slip}), and adding prompts can lower that attention. Whether F2's additional prompts, which are mostly correct updates, are better tolerated than the baseline's is an empirical question for a user study.

\textbf{Why the missed-update problem is easy to overlook.} A missed update does not produce an error message, a wrong answer on the turn it occurs, or a prompt. It surfaces later, when the assistant states an outdated fact. Evaluations that look at single-turn extraction, or at accuracy of what is written, will not see it; measuring the final memory state against the true state, as we do, does.

\textbf{Choosing between larger prompts and better search.} F2 enlarges the prompt by about a third, and in the selection study a plain list of the same size reached as many targets. Keyword and fused rankings did no better; a cross-encoder reranker over the 50 best matches did, by about four points at the same list size, at the cost of one reranking pass per message. About one target in thirteen at $N=350$ was out of reach of every method we tried. Closing that gap needs a different mechanism: a second extraction pass over the whole store when a change is suspected, or a structured memory with typed slots in which an update names its slot. A learned admission gate \cite{zhang2026memgate} could make larger lists safer but cannot raise reachability on its own. We did not evaluate these; the point is that reachability is a quantity worth tracking whichever remedy is chosen, and that simple remedies should be compared against plain larger lists before they are credited.

\textbf{On F1.} Letting a rejected change return only after new user input is cheap and conceptually neat, but we found no benefit with real models (the oracle user rejected no correct change in these runs), and only small, uncorrected-significance effects in simulation. Its value would have to be shown with real users who slip.

\section{Threats to Validity}
\label{sec:threats}
\textbf{Synthetic and English personas.} Personas, unrelated memories and the wording of changes were written by the authors from templates. The change cues of F2 were designed after the reachability failures were seen on the first generator, so F2 may be tuned to it. The second test set (Sec.~\ref{sec:selection}) reduces this risk with a held-out, cue-free half, and it shows that F2 does depend on the cue words; but it is still template-based and written by the same team, and the LongMemEval check is the only independent text. \textbf{Small real samples.} 12 personas, one seed per cell and two models of the same family; exact sign tests with 12 pairs cannot resolve small effects, and several F1 results are inconclusive rather than null. \textbf{Simulated user.} The real runs use a perfect reviewer, the simulations a random slip. Real users may ignore, batch or rubber-stamp prompts; whether additional prompts are tolerated is open. No user study was done. \textbf{Single annotator and scorer.} Labels come from the author. \textbf{One embedding model.} Reachability depends on MiniLM and the 0.25 threshold. \textbf{LongMemEval.} Thirty questions, a judge that is not the official prompt, an oracle reviewer, and a single seed. \textbf{Multiple tests.} Reported as counts; only the large effects are robust to correction. \textbf{Related work.} Six of the closest works were read in full, the others at abstract level; the search was targeted, not systematic.

\section{Future Work}
\label{sec:future}
\textbf{User study.} The most important missing piece is a study with real users that measures how often they approve, reject or ignore proposals, whether they slip, and whether the extra prompts from F2 are tolerated. \textbf{Isolating each factor with real models.} An \emph{oracle-target} run, in which the true target is always added to the prompt, would measure $P(O\mid R)$ directly and show how much error remains once reachability is fixed; a real-model run of the same-budget list would show whether its equal reachability gives equal end-to-end results. \textbf{Better candidate selection.} About one target in thirteen is out of reach of every method we tried, a cross-encoder reranker included; per-sentence reranking, slot-typed memories and a second pass over the store are the next candidates. \textbf{Other languages and models.} All personas are English and both extractors are Gemini models. \textbf{Bigger real samples.} More personas, more seeds, and all 78 LongMemEval knowledge-update questions would turn several inconclusive results into findings. \textbf{Proactive use of memory.} \aura\ also contains an optional layer that asks the user whether a stored fact is still true, sends reminders and prepares briefings; its checks use the same proposal path as the gate. We did not evaluate it and make no claim about it here.

\section{Conclusion}
A review gate on memory changes is effective against the errors it can see: in our experiments it removes almost all of the true facts that automatic application destroys. It cannot repair updates the extractor never proposes, and in a retrieval-based design these are governed by which memories reach the extractor's prompt. We made this precise (an update can succeed only if its target is in the prompt, and the gate acts only after that), measured it, and identified what moves it: removing the minimum score and searching per sentence each raise reachability by about ten points, extra candidates on a change cue add little on their own, and an adaptive selection is matched by a plain larger list, which it beats only in prompt size. With two real Gemini extractors, the adaptive selection (run together with the re-proposal rule) left no change target missing and no stale fact under the gate, at about a third more prompt tokens, while keyword and fused rankings did no better than a plain larger list, a cross-encoder reranker did better at the same list size, and about one target in thirteen remains out of reach of every method tried. The practical lesson for user-controlled memories is to measure and report what the extractor can reach, and to compare any remedy against a plain larger list. Evaluating with real users, with an oracle-target condition, in other languages and with larger real samples is the next step; the code, both test-set generators and every raw result file are provided.

\section{Scoring Rules and Labels}
\label{app:scoring}
\textbf{Value matching.} Each persona slot has a set of possible values (for example the gym slot has ``6 am'', ``7 am'', ``6 pm'', ``8 pm''), each with alternative spellings (``6am'', ``6:00 am'', ``18:00''); birthdays accept ``12 March'', ``March 12'', ``12th March'' and so on; coffee values accept ``black coffee'' or ``oat milk''. A value is matched as a whole word, case-insensitively. Distractor values (a hypothetical city, a friend's car) have their own matchers.

\textbf{Wording of third parties, hypotheticals and ended facts.} A memory that mentions only a distractor value is \emph{third-party} if it contains a word for a relative, friend, colleague or neighbour, \emph{hypothetical} if it contains ``if'', ``would'' or ``hypothetical'', and \emph{false} otherwise. A memory about a retired fact is \emph{ended} if it contains a phrase such as ``no longer'', ``finished'', ``wrapped up'', ``between projects'', ``stopped'', ``sold'', ``unemployed'' or ``not working'' and the fact was retired but not asked to be forgotten. A fact that the user asked to forget and that is still stored counts as \emph{stale}.

\textbf{Annotation protocol.} For every memory in the baseline and F1+F2 real runs the annotator saw the persona's sessions, the true final state and the memory text, and wrote one of seven labels (true, ended, stale, false, hypothetical, third-party, other), looking at the automatic label only afterwards where possible. The automatic and the hand label were then compared (Table~\ref{tab:agree}).
