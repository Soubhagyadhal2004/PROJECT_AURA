# Results: user-controlled memory in AURA (Direction A)

Generated by `npm run eval:results` (eval/build-results.mjs) on 2026-10-13; every number below is computed from the run folders named in each section. Do not edit numbers by hand: re-run the experiment, then this script. How the experiments work: [README.md](README.md).

**Status of the evidence.** Experiments 1-3 use AURA's real memory code, database and local embedding model (Xenova/all-MiniLM-L6-v2) with a **simulated** extractor and a simulated user: they measure the system's mechanics, not Gemini's judgement. Experiment 4 uses the **real** Gemini extractor (Gemini gemini-3.5-flash-lite) on 4 personas per policy: enough to see which errors a real model makes, too few for firm rates.

## Finding 2: the gate depends on a careful user, and a mistaken "keep" is never asked again

`results/gate-sim/v2-20261013/`, user sweep at e = 0.1

| u | gate F1 | gate stale | gate wrong changes applied | gateAll F1 | gateAll wrong changes applied |
|---|---|---|---|---|---|
| 0 | 0.808 | 1.75 | 0.02 | 0.828 | 0.02 |
| 0.1 | 0.783 | 2.00 | 0.28 | 0.763 | 0.17 |
| 0.2 | 0.757 | 2.33 | 0.42 | 0.730 | 0.27 |
| 0.3 | 0.732 | 2.52 | 0.62 | 0.669 | 0.57 |

AURA does not propose a change again after the user turns it down (`propose()` in `server/memory.mjs`). That avoids nagging, but one mistaken rejection of a correct update keeps the old fact for good: stale facts rise from 1.75 to 2.52 as u goes from 0 to 0.3. Prompt precision also falls as the extractor gets worse (1.00 at e = 0 to 0.30 at e = 0.3), so users see more wrong cards exactly when the gate matters most.

AURA lets the extractor change only memories shown in its prompt: `searchMemories(text, 12)` plus the 8 most recent, and `searchMemories` drops everything scoring below 0.25. Even in a store of only 12 memories, search never retrieved the car fact for "I sold my old car and bought a <new car>." (0 of 30 stores); it was reachable only when it happened to be among the 8 most recent (20 of 30). When the target is missed, the old fact stays active next to the new one. Forget requests are hit hardest (0.649 at N = 350). In Experiment 1 this is the main source of stale facts: 27% of change turns missed their target under the gate at e = 0.

## Finding 5: the fixed minimum score in memory search trades recall for noise, and no single cut-off is good

`results/retrieval/v2-20261013/` (726 questions about stored facts and 714 about never-stated ones per store size)

|---|---|---|---|---|---|
| 25 | 0.994 / 1.000 | 0.933 / 0.664 | 0.854 / 0.367 | 0.707 / 0.200 | 0.636 / 0.090 |
| 100 | 0.968 / 1.000 | 0.915 / 0.807 | 0.853 / 0.508 | 0.705 / 0.353 | 0.636 / 0.230 |
| 350 | 0.891 / 1.000 | 0.883 / 0.854 | 0.832 / 0.619 | 0.700 / 0.490 | 0.636 / 0.339 |

Cells: found (right fact in the top 6) / noise (never-stated questions that still return memories). With AURA's 0.25, 28%-29% of questions about a stored fact return **no results at all**, and 29.3% of right answers score below the cut-off; yet at N = 350, 49% of questions about things never stated still return unrelated memories. Keyword-only fallback search: hit@6 0.606. The re-scoring used for the variants reproduced AURA's real `searchMemories()` results in 2178 of 2178 queries. This matters once a user has more than 30 memories; the 30 most recent are always in the Live prompt.

## Finding 6: what the real Gemini extractor gets wrong

`results/real-gemini/20261013-130739/` (Gemini gemini-3.5-flash-lite; 4 personas x 1 seed(s) per policy; u = 0; candidate selection default (0.25); scored with eval/lib/loose.mjs, see rescored.md)

| policy | n | F1 | precision | recall | ended | stale | false | hypothetical | third-party | true facts destroyed | prompts / 100 turns | cards judged right / wrong |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| auto | 4 | 0.916 ± 0.027 | 0.846 | 1.000 | 0.50 | 0.50 | 0.25 | 0.50 | 0.75 | 0 | 0.0 | 0 / 0 |
| gate | 4 | 0.914 ± 0.063 | 0.846 | 1.000 | 0.00 | 0.75 | 0.00 | 0.50 | 0.50 | 0 | 24.6 | 20 / 1 |

- Gemini destroyed **0** true facts in 8 persona runs (170 extraction requests, about 572 input / 39 output tokens each, mean latency 5.2 s). In these scenarios the destructive errors the gate is built for did not occur; its measured benefit here is therefore nil, and the case for it rests on Finding 1 (it is cheap insurance when they do occur).
- Its errors are of two other kinds. **Stale facts** where the old memory was not shown to it (Finding 3), e.g. "The user drives a Seltos.", "The user lives in Bhubaneswar.". **New facts that should not have been stored**, which the gate does not review: hypotheticals ("The user would spend every evening on the beach if they moved to Goa."; "If the user had a cat, they would name her Luna."; "The user would name a hypothetical cat Luna.") and misreadings ("The user wants to move to Goa someday.").
- It also wrote correct memories in forms a strict checker would miss: facts about people in the user's life ("The user's friend Rohan bought a Thar."; "The user's cousin works at Google in Zurich.") and retirements written as updates ("The user finished leading project Lotus last week and is currently between projects as of October 2026."; "The user finished leading the Nimbus project and is currently between projects as of October 2026."). The scoring rules were extended for these after the run (eval/lib/loose.mjs) and re-checked against exact scoring.
- During the run the simulated user turned down 1 review card(s) it judged wrong with the rules in place at the time. Cards were not logged in this run, so which one is not known; a retirement written as an update (above) would have been turned down, so the gate row may be slightly pessimistic until the run is repeated.

## Checks

- Value-based scoring (used for Gemini's wording) vs. exact scoring on simulated runs: 30 of 30 persona runs identical; the two review judges agreed on 208 of 208 decisions (`results/real-scorer-check/v2-20261013/`).
- Retrieval re-scoring vs. AURA's real search: 2178 of 2178 queries identical.
- Consistency: personas average 20.5 user turns, 4 of them distractors. Injected wrong changes per persona (0.82, 1.75, 3.10, 4.97 at e = 0.05, 0.1, 0.2, 0.3) equal e x 15.5-17.5, as expected (a wrong change is skipped when no true memory is shown). Every review card was correct at e = 0 (prompt precision 1.00).
- Simulation runs use a simulated clock (1 ms per call), so they are exactly repeatable; a repeated slice of Experiment 1 matched the full run field by field.
- `npm run test:server` passes with the instrumentation and the option added.

## What the paper can claim, and what it cannot yet

Supported (Experiments 1-3, simulation with AURA's real code):
- Gating changes to existing memories prevents almost all destructive errors (94-98% fewer at e = 0.05-0.3) for 20-33 prompts per 100 turns; gating new facts too costs about 2.8x the prompts.
- F1 over the user's facts understates the harm of auto-applied wrong changes.
- Candidate selection limits what the extractor can change (25%-31% of change requests miss their target with 25-350 other memories), and selecting the 12 best matches without a minimum fixes most of it.
- Not re-asking after a rejection makes the gate sensitive to user mistakes.

Supported by Experiment 4 (small sample, real Gemini):
- The real extractor's errors are mostly stale facts (unreachable targets) and new facts that should not be stored (hypotheticals, misreadings); it made no destructive changes here.

Not supported yet:
- Rates for Gemini's errors with confidence intervals: needs more personas (Experiment 4 had 4 per policy).
- Anything about real users (burden as felt, trust, time per decision): needs a user study.
- Comparison with Mem0 / LongMemEval numbers: different data and tasks; run AURA on LongMemEval before putting numbers side by side.
- Novelty of the approval gate: the literature search so far was not exhaustive.

## Limitations

- Personas average 20.5 user turns over 5 sessions; long-term effects over months are extrapolated.
- Scripted personas written by the evaluator: 12 fact types, short third-person facts, English only; paraphrase coverage is limited (3 per change in Experiment 3, 1 per change elsewhere).
- The simulated extractor's errors are independent and uniform; Experiment 4 suggests a real model's errors are concentrated on new facts, not on changes.
- The simulated user reviews at the end of each session, with a fixed slip rate.
- Labels for Gemini's wording come from rules (eval/lib/loose.mjs); check them by hand with the annotation sheet (`npm run eval:rescore`) before publishing.
- One embedding model (MiniLM-L6), at the quantised size AURA ships; the largest store tested has 350 background facts.
